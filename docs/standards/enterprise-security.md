# Enterprise Security Standard

This standard extends [Security Standards](security.md) for production and enterprise application reviews. Apply the relevant controls when a change affects a trust boundary, identity, sensitive data, internet exposure, a privileged workflow, or a critical dependency. Use [Enterprise DevOps](enterprise-devops.md) for build, release and operational controls. Project requirements may add controls; document conflicts and get an explicit decision from the accountable owner. This standard is a verification baseline, not a compliance certification.

## Required controls

| ID | Control | Minimum evidence |
|---|---|---|
| ES-01 | Assign a service owner. Identify protected assets, data classes, actors, entry points, integrations, and trust boundaries. For material changes, document abuse cases and intended controls before implementation. Keep an inventory of exposed routes, services and dependencies. | Data flow or scope record, affected assets and owners, material threats and acceptance cases. |
| ES-02 | Use approved identity providers and enforce least privilege. Require MFA for privileged human access and separate human, service and break-glass identities. Prefer short-lived workload credentials. On every protected operation enforce server-side function, object, tenant and applicable field authorization. Derive identity and tenant from trusted context; fail closed. Revoke access promptly and review elevated grants. | Role/access matrix, trusted tenant boundary, tests for unauthenticated, wrong role, wrong tenant and permitted requests; evidence for access review when in scope. |
| ES-03 | Validate against allowlisted schemas at trust boundaries. Use parameterized data access, context-aware encoding and safe render sinks. Where rich HTML is necessary, use a vetted sanitizer. Enforce CSP on web responses and define CORS, CSRF and session protections based on actual authentication and origins. Bound upload sizes, redirects, resource consumption and abusive calls. Isolate untrusted URL fetches and reject private/metadata destinations unless explicitly permitted. | Source-to-sink trace; rejected input, dangerous content and cross-origin tests; actual headers or clearly labeled static-only evidence. |
| ES-04 | Minimize and classify data. Use encrypted transport and approved storage/key management for sensitive data. Use scoped service identities and managed secrets; never expose secrets in source, client state, build output, prompts or logs. Separate environments and restrict exports. Define retention, deletion, backup and access based on business and applicable obligations. Treat suspected exposed credentials as incident material: escalate and rotate through the authorized owner. | Data inventory and retention owner; encrypted boundaries and access policy; redacted secret-scan and export-control results. Never include credential values. |
| ES-05 | Record security-relevant authentication, authorization and privileged actions with timestamps, outcomes and correlation IDs. Minimize and redact sensitive fields. Restrict and protect audit log access; define retention and alert ownership. Avoid stack traces and internal error details in public responses. | Sanitized sample events, access/retention policy, failure-path tests, and escalation routing. |
| ES-06 | Admit maintained, trusted dependencies and verify package identity. Preserve lockfiles, review transitive changes and address vulnerabilities according to the project's severity/exposure policy. For production artifacts use the inventory and provenance controls in Enterprise DevOps. | Dependency diff, vulnerability report tied to the revision, remediation disposition, and artifact evidence when applicable. |
| ES-07 | Treat model output, retrieved content and tool results as untrusted. Keep authorization out of prompts alone; validate structured output, allowlist actions and scope data/credentials at the tool boundary. Require an explicit approval boundary for privileged effects. Test prompt injection, data exfiltration and tool misuse where AI or automation is in scope. | Actual tool policy and negative tests; evidence that an injected request cannot grant itself access or cause an unauthorized effect. |
| ES-08 | Track vulnerabilities to an owner, severity, evidence and remediation target under the project's approved policy. Escalate active exploitation and critical findings promptly. Maintain incident contacts, containment and recovery playbooks. Preserve evidence securely and exercise incident response. | Finding and owner; tested remediation or time-bounded exception; incident playbook and exercise/response record when applicable. |

## Review and release decision

- Establish the exact repository, revision, environment and permitted evidence. Distinguish code inspection, tests actually run, scanner output actually obtained and tests still proposed. Record missing evidence as unverified. Do not infer exploitability, absence of vulnerabilities or regulatory compliance from a partial review.
- Rank findings by impact, exposure, exploit prerequisites and evidence. Each finding includes control ID, affected location, evidence, impact, recommendation, owner and verification needed. Use the [ticket lifecycle](ticket-lifecycle.md) when work is ticketed.
- Block the affected release recommendation for an unresolved material control failure, an unverified mandatory control or an outstanding approval. Report the exact blocker and its owner. A documented exception identifies the risk, rationale, compensating control, accountable approver, expiration, and recheck; it cannot waive applicable mandatory obligations. Reviewer advice does not authorize a release or live security testing.
- Close a finding after the authorized fix is tied to the reviewed revision and its regression evidence is verified. Preserve redacted evidence with approved access and retention.
